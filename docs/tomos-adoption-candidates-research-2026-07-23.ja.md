# TOMOSへの新規導入候補に関する調査報告

更新日: 2026年7月23日

## 作業対象

- TOMOSへ追加を検討するモデル、音声技術、Skill管理、PC診断、端末間連携の方針整理
- 公式情報と現在のTOMOS実装を踏まえた優先順位の見直し

## 触らないもの

- モデルのダウンロード、削除、再配布
- 外部バイナリ、外部API、外部サービスの実行
- Agent-Reach本体と外部サービス認証
- 本番環境、公開リリース、ユーザーデータ

## 総評

現時点で優先すべきなのは、モデル数を増やすことではない。

1. PC環境と用途に応じたモデル選択
2. 既存ASRを生かした低遅延音声会話
3. Skillと業務手順の蓄積
4. ローカルAIとしての安全性と使いやすさ

ユーザーにはモデル名を並べず、「標準AI」「コード作業」「高性能AI」「音声」のように用途を先に見せる。新しい候補は、ライセンス、配布元、実機性能、安全性を確認してから段階的に追加する。

## 1. モデル構成

### 初期版で維持する構成

#### 標準AI

`Qwen3-4B-Instruct-2507`

- 学生や一般的な16GB PC向けの標準候補
- 通常会話、Knowledge検索、教材パック、軽いツール実行を担当
- 公式モデルはApache 2.0
- 256Kコンテキストは上限値であり、実際の利用時はメモリに合わせて短くする

#### コード作業

`Agentic Coder v2`

- 取得済みの場合だけ、コード生成、修正、レビューで優先
- 全学生への必須ダウンロードにはしない
- TOMOS内の表示名であり、一般的な公式製品名ではない
- 現在の設定値は `hf.co/yuxinlu1/gemma-4-12B-agentic-fable5-composer2.5-v2-3.5x-tau2-GGUF:Q4_K_M`
- 現在の正確なモデルID、ベースモデル、ライセンス、配布元、再配布条件をリリース前に確認する
- 出所またはライセンスを確認できない場合は標準候補へ昇格しない

#### 任意の高性能AI

`Gemma 4 12B` / Apple Silicon向けMLX版

- 高性能会話、画像理解、比較検証の任意候補
- 学生PCへ必須取得させない
- PC環境によってはE2BやE4Bより配布ファイルが小さく見える場合があるため、モデル名ではなく実際のファイルサイズ、メモリ使用量、速度で判断する

### 比較実験

- Gemma 4 E4B
- Gemma 4 E2B
- Ornith 1.0 9B
- Gemma公式版とUnsloth量子化版

Gemma 4 E2Bの「E」は実効パラメータを表す。埋め込みを含む総量は約5.1B、E4Bは約8Bであるため、名称だけで軽量と判断しない。Ornith 9Bは新しいエージェント・コード作業向けモデルとして扱い、公式のベンチマーク値だけで採用せず、TOMOSの実作業で比較する。

### 配布形式

- GGUF: Windows、Mac、Linuxで利用可能。TOMOSでは主にOllamaまたはllama.cpp系で検証
- MLX: Apple Silicon向け
- QAT: 低メモリ専用形式ではなく、量子化を考慮した学習方式
- NVFP4: 主にRTX 50系などBlackwell世代GPU向け。対応ランタイムを確認してから使用

Unsloth版は無条件に標準化しない。公式版との差分、品質、量子化方式、モデルライセンス、配布元、更新元を確認する。

## 2. 音声AI

音声は、差し替え可能な処理として分離する。

```text
マイク入力
  -> VAD / 発話区切り
  -> STT
  -> 用途別モデルルーター
  -> LLM
  -> TTS
  -> 音声出力
```

TOMOSには録音UI、ASR API、Nemotron、Whisperの既存経路がある。新しい音声基盤を別に作らず、この経路へVAD、常駐処理、TTS、割り込みを追加する。

ジャービス感はLLMの性能だけでは決まらない。次を一体で測定する。

- 発話終了から最初の文字までの時間
- LLMが最初の文章を返すまでの時間
- 最初の音声が出るまでの時間
- 読み上げ中の割り込み
- LLMと音声モデルの同時実行時のメモリ使用量
- 会話履歴とMemoryの反映

### VibeVoice Realtime 0.5B

位置づけ: PoC優先度は高い。標準採用は実機合格後。

ストリーミングテキスト入力に対応し、公式説明では最初の音声まで約300msを目標としている。ただし、公式も実運用には追加検証が必要としているため、最初から標準音声にはしない。

検証項目:

- 日本語の自然さ、読み間違い、数字と固有名詞
- 実測の初回音声遅延
- Windowsでの導入と起動
- CPUのみ、内蔵GPU、低VRAM環境での速度
- LLMとの同時実行時の負荷
- オフライン起動と外部通信の有無
- モデルと音声プリセットの利用条件

### Qwen3-TTS

位置づけ: PoC優先度は高い。

- 0.6B: 軽量なCustomVoice / Base候補
- 1.7B: 品質優先のCustomVoice / Base候補
- VoiceDesign: 自然言語の説明から新しい声を設計する1.7Bモデル
- Base: 許諾済み参照音声によるボイスクローン候補

初期PoCでは、個人の声を保存しないVoiceDesignまたはCustomVoiceを優先する。Baseを使う場合は、本人または権利者の明示許諾、利用目的、保存先、削除方法、共有禁止を先に設計する。

### VibeVoice ASR 7B

位置づけ: 会議録用の実験候補。

最大60分の長時間音声を対象に、話者、タイムスタンプ、内容を含む構造化文字起こしができる。通常のリアルタイム音声入力には重いため、既存Whisperを置き換えず、会議録専用で比較する。

```text
会議録音
  -> 話者・時刻付き文字起こし
  -> ユーザー確認
  -> 要約・決定事項候補
  -> 保存承認
  -> Knowledge / Memory
```

文字起こし結果や要約は、ユーザー確認なしでMemoryへ保存しない。

### ZONOS2

位置づけ: Linux / NVIDIA限定の実験枠。

ZONOS2は日本語をTier 1として扱う一方、現在の公式ローカル実行条件はLinux x86_64とNVIDIA GPUである。学生向けやWindows標準にはせず、高品質音声、ボイスクローン、事前生成、キャッシュ用途で検証する。

## 3. Markdown Skill Manager

導入候補: 非常に高い。

TOMOSでは次の4つを分ける。

- Knowledge: 何を知っているか
- Memory: 何を覚えているか
- Skill: どう仕事をするか
- Plugin: 何を実行できるか

Microsoft SkillOptは、固定したLLMに対し、自然言語のSkillを実行結果から改善する研究・実装である。TOMOSとの相性はよいが、初期版へSkillOpt本体を組み込む必要はない。

初期版ではMarkdownを正本とし、手動レビューで昇格する。

```text
Skill実行
  -> 結果評価
  -> 失敗理由を記録
  -> Skill候補を改善
  -> 固定した検証例で再確認
  -> 担当者が承認
  -> best_skill.mdへ昇格
```

最低限記録する項目:

- Skill ID、名称、目的
- バージョン
- 対応する入力と出力
- 使用モデル
- 必要なPluginとデータ参照範囲
- 成功条件
- 成功件数と失敗件数
- 失敗事例
- 外部通信と外部書き込みの有無
- 作成者、レビュー者、承認者

成功率だけで自動昇格させない。評価に使った例と改善に使った例を分け、機密情報をSkillへ直接書き込まない。

## 4. PC診断とllmfit

導入候補: 考え方は採用。本体組み込みは保留。

llmfitはCPU、RAM、GPU、VRAMなどを検出し、モデルの適合度、速度、コンテキストを推定する。TOMOSの初回セットアップ体験の参考になる。

```text
ローカルPC診断
  -> 用途を選択
  -> TOMOSの許可済み候補から提案
  -> 短い実機ベンチマーク
  -> 結果と必要容量を表示
  -> ユーザー承認
  -> ダウンロード
```

llmfit本体は、ダウンロード・削除機能や外部の実測情報を扱う。また、通常起動時にWebダッシュボードを `0.0.0.0` で開く構成がある。TOMOSから無監査で実行しない。

TOMOS側の要件:

- 診断はローカル・読み取り専用
- 外部通信は初期OFF
- Web待ち受けが必要な場合はlocalhostのみ
- 推薦対象はTOMOSのホワイトリストに限定
- 理論値と実測値を分けて表示
- 自動削除を行わない
- ダウンロード前に保存容量、配布元、ライセンスを表示
- ダウンロードとインストールは必ずユーザー承認後
- 診断結果を外部送信しない

既存のTOMOS PC診断とModel Routerを先に監査し、不足している判定だけを追加する。

## 5. AlterSend

導入候補: 将来の独立PoC。

AlterSendは、アカウントやクラウド保存を使わないP2Pファイル転送を掲げる新しいOSSである。TOMOSの初期機能には入れず、Knowledge Layer完成後も自動的には統合しない。

想定用途:

- PCとスマートフォン間のKnowledge候補の受け渡し
- 同一利用者が所有するTOMOS端末間の共有
- 承認済みSkillパックの移動

統合前に確認する項目:

- DHT上へ公開される端末情報
- NAT越えと中継経路
- 端末認証とペアリング解除
- 暗号鍵の保存先
- 受信前確認と上書き防止
- ファイル名、サイズ、ハッシュの検証
- 会社データの持ち出し制御
- ライセンスと更新元

Company Memoryや会社内共有には、管理者ポリシー、監査ログ、端末失効が必要であり、個人向けP2Pと同じ設計にはしない。

## 6. Kawaii Agent V2

位置づけ: 競合・体験設計の参考。

ローカルLLM、VRM / MMD、Whisper、VOICEVOX、会話記憶、表情、モーション、親密度などを組み合わせたデスクトップAIキャラクターである。ローカル実行だけでなく外部AIにも対応するため、「完全ローカル」という表現だけで安全性を判断しない。

方向性の違い:

- Kawaii Agent: キャラクターとの交流が中心
- TOMOS: 個人AI秘書、仕事、Knowledge、Memory、Skillが中心

参考にすべきなのは、モデル名ではなく体験を見せる設計である。

- 自分を覚えてくれる
- 声で話しかけられる
- 資料を探してくれる
- PC作業を手伝ってくれる
- 仕事のやり方を一緒に育てられる

業務PCで競合製品を実行する場合は、コード署名、外部通信、保存データ、ファイル操作権限、利用規約を確認する。

## 7. 推奨優先順位

### 優先度A: 現在のTOMOSへ反映

1. 既存Model RouterとPC診断の差分監査
2. Qwen3-4B-Instruct-2507を標準AIとして維持
3. Agentic Coder v2の由来、ライセンス、再配布条件を確認
4. 既存ASRへ接続するTTS共通インターフェースを設計
5. VAD、常駐ASR、割り込み、遅延計測を追加
6. Markdown Skill Managerを手動レビュー方式で設計
7. PC診断の理論値と短い実機ベンチマークを分離

### 優先度B: 比較PoC

- VibeVoice Realtime 0.5B
- Qwen3-TTS 0.6B / 1.7B
- Gemma 4 12B / E4B / E2B
- Ornith 1.0 9B
- 公式版とUnsloth量子化版
- VibeVoice ASR 7B
- ZONOS2

### 優先度C: 評価基盤完成後

- SkillOptを参考にしたSkill改善支援
- P2P端末同期
- 会社内Skill共有
- Company Memory
- 企業サーバー接続
- VRMアバター統合

### 学生画面・初期版から除外

- GLM-5
- gpt-oss-120B
- DeepSeek大型モデル
- Coder v1
- ZONOS2の標準採用
- モデルの自動削除
- 未監査の外部バイナリ自動実行
- ユーザー確認なしの外部通信、ダウンロード、Memory保存

## 8. 共通の合格条件

候補ごとに、次の項目を実測してから採用を決める。

- 対象PCとOS
- モデルファイル容量
- 起動時の最大メモリ
- 実行中の最大メモリ
- 初回応答時間
- 継続速度
- 日本語品質
- オフライン動作
- 外部通信先
- ライセンスと再配布条件
- 供給元とファイルハッシュ
- 失敗時に既存経路へ一度だけ戻れること
- アンインストールまたは無効化で既存機能が壊れないこと

音声では、STT、LLM、TTSを単体と同時実行の両方で測定する。Skillでは、改善用事例とは別の固定検証例で合格を判定する。

## 結論

TOMOSはモデルを大量に並べる製品ではなく、次の体験を安全に提供する方向へ進める。

```text
PCと用途に合ったモデルを選ぶ
  + 低遅延で声を返す
  + ユーザーの確認を経て記憶する
  + 仕事のやり方をSkillとして育てる
  + 外部通信とツール実行を安全に制御する
```

次の作業は、3本の実装指示を同時に作ることではない。まず既存Model Router、PC診断、ASRの差分を確認する。その後、Voice PoC、Markdown Skill Manager、PC診断改善を独立した工程として順番に設計する。
